# `tools/llm-eval/`: does the optional on-device LLM add value over parser v2?

Maintainer-only. It makes no network requests and uses no npm dependencies.

This harness measures the optional LLM from stage 2 Step 4 against parser v2,
the deterministic "certain or nothing" parser in `src/parse.js`. The app ships
the deterministic path first; the LLM is only worth the risk if it recovers
answers without ever adding a wrong value or changing a routing answer.

v0 runs only the deterministic parser-v2 baseline. The LLM backend and the JVM
`:llm-core`/`:llm-eval` modules are not built yet, so the go/no-go decision
stays open.

## Run

From the repository root:

```bash
node tools/llm-eval/sets.mjs
node tools/llm-eval/index.mjs
```

`sets.mjs` writes `sets/*.jsonl` deterministically. `index.mjs` checks that the
sets are fresh, runs parser v2 over them, writes `reports/v0-parser-v2.{json,md}`
and prints the Markdown report. It exits 0 when the parser-v2 gates pass and 1
on a parser-v2 regression. An unavailable LLM is not an error.

## Case format

One JSON object per line, with keys in this order:

```
{ id, set, category, type, questionKey, optionsKey, transcript, expected }
```

- `questionKey` and `optionsKey` are a schema question id or `null`.
- `expected` is the expected value, or `"U"`, which means "must defer".
- In the coverage set, `expected` is `null`: those cases are unlabelled.
- Audio cases add `wav` after `expected`; they need speech-to-text, so v0
  records them but does not run them.

The files under `sets/` are generated by `sets.mjs`. Never edit them by hand.

## Sets in v0

- **routing**: the 164 value cases from the shared parse corpus. Parser v2 must
  keep answering all of them, so the LLM must never be invoked.
- **adversarial**: the 73 defer seeds from the same corpus. Every one must
  still defer.
- **coverage**: type probes (8 per text question, up to 10 per choice question,
  10 each for number and monthyear) for every askable question. Unlabelled
  counts show the gap an LLM would have to fill.
- **audio**: the 9 speech fixture WAVs, not run in v0.

## Ship gates

Copied from "Ship gates" in `on-device Android app for the disability forms
assistant.md`:

- 0 wrong values read back on the adversarial set, for every type and every CPU
  class. Any failure blocks the release.
- ≤ 0.5% wrong on text, with no dropped content words.
- ≥ 40% of answerable-but-deferred cases recovered, **otherwise the LLM doesn't
  ship**.
- Routing set 100% unchanged.
- The latency gates above.

- At least 400 human-reviewed adversarial cases.
- Labelled coverage.
- The audio set through speech-to-text.
- The go/no-go entry in `TODO.md`.

`parser.mjs`'s backend split mirrors `AnswerParser`/`Provenance` in
`android/llm/src/main/kotlin/org/ssa/assistant/llm/AnswerParser.kt`: the
deterministic parser is always present, the LLM is optional, and its output
must pass the deterministic verifier before it counts.

## Data rules

Everything here is synthetic. SSNs come only from the non-issuable range
(`987-65-4320` through `987-65-4329` in the speech fixtures).
